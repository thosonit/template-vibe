# Git workflow

Source of truth for git behaviour in this repo (generated by the `git-conventions` skill; re-run the skill to change it).
## 1. Branching model

GitHub Flow. One permanent branch: `main` (always deployable; every merge is a release).

| Branch | Branches off | Merges into | Naming |
|---|---|---|---|
| Work | `main` | `main` | `feat/`, `fix/`, `docs/`, `chore/`, `refactor/<short-description>` |

- `<short-description>` is kebab-case, e.g. `feat/auth-login-screen`. No ticket ids (no tracker).
- Keep branches short-lived; update from `main` before merging back.
- A hotfix is a normal `fix/` branch off `main`.
- Do not commit work in progress directly on `main`.

## 2. Commit messages

Follow the common commit rule (`~/.claude/rules/common/git-workflow.md`). Nothing project-specific is defined here.

## 3. Pull requests and merging

- No PR required (solo, no CI). Merge a work branch with `git merge --squash`, so `main` gets one Conventional Commit per change, then delete the branch locally and on origin.
- Direct push to `main` is allowed for that merge result only.
- Run the stage 4c checks (build, lint, typecheck) locally before merging.

## 4. Release and hotfix

- Continuous: every merge to `main` is a release. No `release/*` or `develop` branches.
- No version tags until the project adopts versioned releases; then tag `vX.Y.Z` on `main`.
- Code reaches `main` only through the merge in section 3; the deploy stage does not add its own merge step.

## 5. AI assistant rules

- Commit only when the user asks. Push to `main` only when the user asks.
- Never force-push `main`.
- Create work branches off an up-to-date `main` using the naming table above.
- Follow this model as written; do not re-derive the workflow or propose Gitflow.
- Never commit secrets (`.env*`, credentials, API keys).
